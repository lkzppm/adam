/adam:setup — the 8-phase scaffold

A strict, dependency-ordered pipeline that turns a virgin repo into a spec-driven Claude Code project. Deterministic shell scripts handle the boring work (graph indexing, template copying, drift checks, token aggregation); the adam sub-agent only burns tokens where judgment matters (stack detection, prose, anchor selection). The final brief reports session-wide token cost so the run pays for itself.

Brief

The setup pipeline is the one place adam writes opinionated artifacts into the user's project. Every other skill (/spec-create, /spec-update, /spec-audit, /claude-add) builds on the layout this pipeline establishes — so order and idempotency matter.

Phases divide cleanly: P0–P2b are mechanical (scripts + a single agent dispatch) and run without user input; P3 is interactive (three AskUserQuestion menus, one per .claude/ artifact class); P4–P5 write the chosen artifacts and the final brief; P6–P7 verify and report.

CLAUDE.md is written last on purpose: it references the actual .claude/agents / .claude/skills / .claude/hooks entries that exist at the time of writing, not a guess about what the user might pick.

Steps

  1. Phase 0 — knowledge-graph bootstrap
    scripts/tools/setup-graph.sh: verifies gitnexus is on PATH (hard stop if missing), runs gitnexus analyze if .gitnexus/ is absent, strips the auto-injected <!-- gitnexus:start --> block from CLAUDE.md (its boilerplate measurably biases the model), and merges a gitnexus entry into .mcp.json. Emits one JSON line the skill parses.
  2. Phase 1 — copy the rules
    scripts/template/write-spec-rules.sh: copies templates/rules/*.md (refactor · additive · orient) into <project>/spec/rules/. These three workflow recipes are project-agnostic and identical across every adam installation; they are the bench-validated behavior contract.
  3. Phase 2 — spec scaffolding
    Agent dispatched in scaffold-only mode. It detects the stack (manifest files, framework markers, top-level subsystem dirs) and writes spec/overview.md, spec/project/<area>.md, spec/concepts/<subsystem>.md, and spec/INDEX.md with token counts via the token-count MCP. A focus instruction from $ARGUMENTS biases which subsystems get deeper coverage. In --merge mode the agent first reads the pre-existing spec/** + CLAUDE.md and ports valuable content into adam's slots instead of writing from scratch. CLAUDE.md is NOT written in this phase.
  4. Phase 2b — pipelines viewer
    scripts/template/write-pipelines-viewer.sh: installs spec/pipelines.html (this viewer) and an empty spec/pipelines/ folder. Individual pipeline-specs (like this file) are written on demand via /adam:spec-create <topic> --pipeline — the setup pipeline never auto-generates them.
  5. Phase 3 — three per-class menus
    Three AskUserQuestion calls — one for hooks, one for subagents, one for skills. Candidates are built from the stack signals the P2 agent returned (Python+ruff → ruff-format hook; FastAPI → route-reviewer agent; etc.). User ticks what they want. Empty classes are silently skipped. This phase is mandatory — no auto-additions, no defaults.
  6. Phase 4 — create only what was picked
    Agent dispatched in claude-add mode for each ticked item. Hooks land in .claude/hooks/<name>.sh (with shebang, chmod +x); .claude/settings.json is merged (read-splice-write-back), never overwritten. Sub-agents and skills land in .claude/agents/<name>.md and .claude/skills/<name>/SKILL.md.
  7. Phase 5 — write CLAUDE.md
    Agent dispatched in finalize mode. CLAUDE.md follows an 8-section structure (project paragraph · stack · runtime shape · spec index table · response style · spec/graph routing · editing rules · refresh pointer). The spec table mirrors spec/INDEX.md with live token counts. In --merge mode, user-authored sections of the prior CLAUDE.md are preserved under a ## Project notes heading.
  8. Phase 6 — spec-lint verify
    The bundled spec-lint MCP validates frontmatter, cross-references, token ceilings, and spec/INDEX.md ↔ CLAUDE.md consistency. Errors are fixed by re-dispatching the agent with the issue list; warnings surface in the brief but don't block. Re-run until errors: [].
  9. Phase 7 — final brief
    scripts/tools/session-token-usage.sh: aggregates message.usage across every assistant message in the current session JSONL, then the skill prints a single brief — graph stats, spec inventory, project automations, CLAUDE.md token count, lint summary, and the new Tokens consumed (this session) line so the user can see what setup cost.

Failure modes

  • gitnexus missing — P0 exits non-zero with npm install -g gitnexus hint. The skill relays it verbatim and stops; every later phase depends on a working graph.
  • spec/ already populated, no flag — the gate after P1 bails out and points the user at /adam:spec-update, /adam:setup --merge, or /adam:setup --force.
  • P2 agent fails to write — the skill stops before P2b (the viewer install is best-effort but the spec tree is load-bearing).
  • spec-lint errors at P6 — re-dispatch loop until errors: []. Warnings are surfaced in the brief but don't block.
  • session-token-usage.sh can't find the session — the brief prints "not available" for the Tokens line. The setup still completes; the metric is optional.
  • User picks zero items in P3 menus — that's fine. .claude/ stays empty; the CLAUDE.md in P5 just omits the "Project automations" subsection.
